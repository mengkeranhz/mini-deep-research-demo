# 通用行程规划

本技能只换研究对象与产物形态，不豁免也不替代宿主的研究纪律：locate_sources 定权威域名、web_search 优先 domains 限定、关键数据逐条
record_facts 入账——里程、耗时、价格、时刻与任何断言同等对待，账本无条目就不写；终答前双向对账。宿主无对应工具或账本时，用可用的检索与地图工具替代，数据纪律与来源对账不变。下面的流程与自检是行程维度的补充，不替代账本对账。

**入账范围**
（行程维度）：锚点口径（班次、闭馆/停检、放票与退改、施工/封闭/限行通告）、地图实测值（车程、里程、净增量、海拔）、容量口径（游览所需时长、排队、限流）、定性断言（避雷原因、方向与窗口理由）——每一条必须写成可机械核对的判据句（弧段走向 / 日期口径 / 官方通告原文），不得只写结论或俗称；写进报告的汇总值（总里程、总时间、总预算与人均）也入账，标"派生"并留加总式；内置口径（休整
10–15 分钟、长驾日 ≥3 小时）与合理默认不入账，默认在总览标"可改"。

北极星：一份拿去就能走的行程——路线顺、时间实、密度合理、风险有底、随时可改。景点介绍只为决策服务（看什么、值不值、待多久），不堆文案。

## 父Agent汇总纪律

- 本技能对父Agent全程生效：初始拆解、子任务契约、子报告合并、最终格式编排与终答自检使用同一套规则；不得只在子Agent执行。
- 子Agent报告只提供结构与叙述线索；父Agent汇总时，所有数值、时刻、价格、路况和确定性断言必须能在合并后事实账本中找到。账本没有的数据要补检索入账，不得凭子报告或记忆改写。
- 住宿可订、道路通行、门票放票、闭馆日等会决定方案成立的依赖必须以 critical=true 入账。若状态不是 found，主方案必须采用不依赖它的保守排法，并在答案中写清「保守主方案」与「升级条件」；未确认项只能作为可选升级，不得作为唯一主计划。
- 父Agent最终报告必须重新执行第 9 节自检，并严格采用第「输出」节的骨架；多版本任务还须执行「多版本规划纪律」及同源数据、冲突核对。核对过程不得新增输出章节；多版本输出增量仅限「横向对比」。

## 多版本规划纪律

- 用户要求多个版本时，父Agent必须先把每个版本名转化为一份「版本契约」，再拆解和委派；不得把版本名直接当作排程参数。
- 每份版本契约包含：
    - **用户可感知承诺**：该版本要放大的体验差异；
    - **主目标**：可优化的方向；不同版本必须对应不同目标，而不是同一目标下的轻微参数变化；
    - **保护约束**：用户硬性要求与安全、法律、交通等不可违反条件；
    - **可交易变量**：为达成该版本目标，允许降低优先级、替换或舍弃的规划要素；
    - **隔离决策变量**：父Agent可共享事实与保护约束，但以下决策必须按版本独立推导：
      环线方向、主干走法、必去点集合、远端走廊取舍、住宿城市序列、
      单日驾驶上限、连住规则、常规出发时间、景点数量；
    - **空间/结构差异约束**：至少在路线方向或主干走法、住宿城市序列、远端走廊取舍、
      单日驾驶结构、景点覆盖数量、用户看图可感知差异六个维度形成可核验差异；
    - **版本专属检索策略**：检索词必须反映该版本目标，不得所有版本共用同一组“目的地+必去”召回；
    - **可验证指标**：从契约推导、且能从本次行程产物中核验的观察维度；不得用固定阈值或通用参数替代推理；
    - **失败判据**：出现哪些表现即说明该版本名不副实。
- 版本契约必须来自用户语境、研究对象和保护约束；不得为任何版本名预设通用参数、必去对象、必砍对象或固定差异幅度。
- **用户明示的交通方式与线路范围不可交易**：若用户要求“自驾”“包车”“公共交通”或指定“大环线 / 小环线 /
  某区域 / 全程”，父Agent必须把它写入每份版本契约的保护约束；版本差异只能改变方向、走法、节奏、取舍、
  住宿和景点密度等实现变量，不得改变交通方式或研究对象范围。
- 父级 required_facts 必须包含「公用·交通方式与线路范围不变量」；每个版本也必须按前缀入账
  「交通方式与线路范围一致性」，值中列明边界交通例外与逐日跨节点主线交通方式。
- 委派子Agent时必须传递对应版本契约。子Agent若发现版本目标与保护约束不可同时满足，应返回冲突说明和需用户取舍的选项，不得静默降级目标后继续沿用版本名。
- 每个 travel-planner 版本子任务的 required_facts 除通用行程事实外，必须显式包含并按版本前缀入账：
   「路线结构决策（方向、主干走法、是否完整大环线）」「必去点集合与景点覆盖数量」「远端走廊取舍」
   「住宿城市序列与连住结构」「单日驾驶结构与常规出发时间」「版本独有看图可感知差异」
   「交通方式一致性」。
- 父Agent不得把“经典环线”或某一版本的具体走法作为公用决策下传；公用事实只用于可行性校验和事实对账。
- 父Agent合并时必须执行**目标分离核验**：
    - 逐版本对照版本契约，核验主目标、可交易变量和失败判据是否真实体现在行程中；
    - 执行标签互换测试：隐藏版本名后，若仍无法从空间结构、时间结构、取舍结果和用户可感知体验中区分方案，判定为版本未分离；
    - 硬性计算并输出以下指标（缺一即不合格）：
       1. **主干节点重合率**＝两版共同核心节点数÷两版核心节点并集数，另列共同主干与各版独有节点/路段；
       2. **住宿城市序列差异**＝逐晚城市对比＋不同过夜点数量/重合率＋连住结构；
       3. **远端走廊取舍**＝逐条列两版“排入/排除/替换”及实测代价；
       4. **单日驾驶结构**＝逐日纯驾时长分布、最长日、平均值/中位数；
       5. **景点覆盖数量**＝门票景点数、核心体验点数、独有点数；
       6. **看图可感知差异**＝隐藏版本名只看路线图/节点序列能否区分，写 PASS/FAIL 与识别特征。
    - 指标未达版本契约设定的分离要求，或只有子Agent自述、没有行程与账本证据时，必须先回炉重排决策变量；
      重排后仍不可分离的，才能在「横向对比」中诚实说明约束冲突、各版本实际定位，以及需要用户选择的约束选项。

## 交通方式不变量

- 用户明示的交通方式是保护约束，不是版本差异变量。自驾请求中，从取车到还车前的跨城市、跨景区、
  跨区域主线转移必须由该租赁车地面驾驶完成；不得把车停在机场/车站后改乘国内航班、火车或长途客车
  制造“飞地”。城内步行、短途打车或公共交通只可作为辅助接驳，不得替代跨节点主线交通。
- 用户明确给出的边界交通例外不得推广到行程内部。例如“D1 飞抵出发城市取车、D9 还车后飞离”
  只允许这两个边界航班，不意味着中途可以再搭乘航班。
- 版本目标与交通方式冲突时，先拒绝违反不变量的结构，改选满足不变量的自驾结构；
  仍不可行则返回冲突说明和需用户取舍的选项。披露代价不能使违反方式的主方案变成合格方案。
- 若用户明确要求“飞机 + 自驾混合”等，上述限制按用户授权放宽；
  未明确授权时一律从严解释。

## 流程

### 1. 解析需求与优先级

- 对照槽位查漏——日期与天数、人数与构成、交通方式、预算、节奏、兴趣、限制（老人小孩/高反/证件）、必去与排除、住宿偏好。
- 缺口按合理默认先跑，在总览里标"可改"；只问对结果影响最大的几个。
- 节奏从需求推断：天数紧、跨度大、自驾长线偏紧凑；带老人孩子、出现"慢/度假"字样偏休闲，拿不准取适中。
- 用户要求多个版本时，先完成「多版本规划纪律」的版本契约，再拆解任务和委派子Agent。

### 2. 生成路线结构假设与建立候选节点库

- **经典路线只能作为候选路线 0，不能直接作为默认答案。** 建立节点池前，必须先生成至少 3 类可比路线结构：
    1. 经典完整环线；
    2. 低强度 / 少点深度结构（可用连住、据点辐射、缩短远端、减少搬酒店实现）；
    3. 非典型方向或替代走廊结构（如反向环线、替代公路、整段替换主干、舍远端换局部深度）。
  三类结构都必须先通过「交通方式不变量」筛查；任何停车后换乘飞机/火车/长途客车，直接淘汰，不得进入目标优化。
  每类结构先给出粗粒度节点/住宿序列、预估里程与驾驶结构、主要收益和风险，再按版本契约选择；
  不允许仅因为“经典”“常见”“必去清单通常如此”而直接采用。
- 召回型查询按版本目标分开设计：高覆盖/高强度版应覆盖“全环线、远端走廊、签名外延、日出日落、时间利用率”等查询族；
  低强度/休闲/深度版应覆盖“少开车、连住、一地深度、小众替代、舒适路线、非典型走法”等查询族；
  另保留一条“目的地+必去/小众/自驾支线/新晋/路况封闭”和一条带时间窗的通用召回。地图地点搜索按区域捞点，主线之外的支线点也进池。
- 检索带回的新点与先验骨架合并后分五层：
    - **必去**（本线签名点，缺了不成这条线）
    - **签名外延**
      （本线标志性体验段，优先级仅次于必去；判定：多源攻略反复点名"本线精华/错过后悔"，且需专门动线才能到达；单列成表，标所属走廊与实测换入代价）
    - **推荐**（值得但有代价）
    - **备选**（换入池）
    - **避雷**（不值得或坑，附一句原因）
- 池是活的：排程中塞不下先调住宿布局与顺序，再按下面的砍点默认顺序动层；有富余从备选池换入。
- **砍点默认顺序**：备选层 → 推荐层 → 签名外延层 → 必去层。签名外延 **不得以"天数锁死"为由直接进取舍**，必须走第 6
  步置换方案模板；确无可行置换时，须列出试过的 ≥2
  个置换组合及各自触硬日的实测数据。与"可替代的打卡型必去点"冲突时，结合景区重要性与代表性、时间预算进行取舍。

### 3. 地理聚类

- 按实测车程（用地图工具实测）与交通方式聚簇，不按行政区划、不按知名度；小簇一天走完，大簇（整城、湖区）连住辐射进出。
- 注意地理上连成一串的节点可能是整段替换某段主干的走廊，不只是从据点往返的支线——评估换入时按重排动线后的净增量算代价（用地图工具实测）。
- **走廊单元**：地理上连成一串、共用一条公路的支线点按一个单元评估，不得拆散逐点算代价、不得整体不换入却单点写进取舍（例：315
  柴达木段 = U 型公路 + 东台吉乃尔湖 + 水上雅丹）。换入代价按往返式与贯穿式两种口径各实测一次、取较小者入账，取舍说明标明口径；主干道封闭改走法后须重做走廊评估。

### 4. 时间预算

- 每天时间账 = 交通 + 游览 + 排队（旺季口径）+ 用餐 + 休整 + 缓冲。缓冲须显式：单列一行写时长与用途，计入当日总量；无时长无用途的"缓冲"按留白处理（终检口径见第 9 节）。
- **领域数据账本**：`skill://travel-planner/schemas/travel-fact.schema.json` 定义地点、路线、锚点、
  时长预算、约束、风险、行程快照等结构化事实。关键领域事实优先用 `record_facts.payload` 入账；
  `schema` 通常指向具体子结构，如 `urn:mini-deep-research:travel-planner:travel-fact:v1#/$defs/route`、
  `#/$defs/anchor`、`#/$defs/duration_budget`、`#/$defs/constraint`、`#/$defs/risk`；
  根 Schema 仅当 payload 本身就是完整 travel-fact envelope 时使用。未覆盖字段放入 `extensions`。
- **机器可读行程产物**：排程定稿后用 `run_code` 生成 `data/itinerary.json`，结构遵循
  `skill://travel-planner/schemas/itinerary.schema.json`
  （`$id=urn:mini-deep-research:travel-planner:itinerary:v1`）。
  Markdown 仍是用户交付物；该 JSON 用于终检、后续修改和多版本对比，生成后将其路径与版本名入账。
- **时长预算也是事实**：早餐、退房装车、加油、取还车、入住、正餐、休整、停车检票等支撑动作，必须按
  `duration_budget` 记录 `subject / context / normal / compressed / minimum / preconditions / evidence`。
  数值从用户语境、行程强度、住宿形态、现场约束或来源推导；无法核实则 status=proxy 并写推导理由，
  不得把某个固定分钟数当成普适答案。
- **现实动作预算库**：本 Agent 运行期间只需读取一次
  `skill://travel-planner/reference/duration-budgets.json`，并将选用的预算入账；后续排程沿用该账本结果，
  不得每日或每版本重复读取同一文件。读取后按其中的 `subject + context` 选择预算。
  该库是领域默认假设，不是普适硬规则；覆盖优先级为：用户明确约束 > 已核实现场事实 > context 默认预算 >
  模型推导。若用户或现场事实覆盖默认值，必须记录覆盖理由与新的前置条件。
- 使用 `compressed` 或 `minimum` 前，必须逐条核对 `preconditions`，并把已满足的动作写入前序行程
  （如前一晚购买打包早餐、整理行李、结清房费、车停门口）。不满足前置条件时使用 `normal`。
- 例如：酒店/餐厅堂食早餐默认 `normal=PT30M`、`compressed=PT20M`，同场景排成 12 分钟不合格；
  若改为 `packed_or_takeaway_simple`，可在满足前一晚采购/打包、无需加热排队等条件下按 `PT10M–PT15M` 排。
- “接缝并入”只适用于无操作成本的余量。凡有实际操作成本的动作，必须先有对应 `duration_budget`；
  拆分耦合行时重新核对该预算并重排后续时间轴，不得机械切分原总时长。
- 服务区休整不是隐形成本：每次 10–15
  分钟，点出可停靠的服务区/城镇名（叫不准就标"以导航实时为准"），作为单独一行，写进当天时刻表——长驾日读者要能看到在哪歇脚、歇几次。
- 图中观景短停，顺道游览，点出具体景点，作为单独一行，写进当天时刻表。
- 接驳行完整性：住宿点与游览点不重合时（含"住在景区旁"），往返接驳各占一行——驾车写 km/min 实测值，步行写 min
  并注明"步行"，不得因"就在旁边"而省略。
- 交通耗时与里程用地图路线工具按实际方式（驾车/步行/公交）实测并入账，同一起讫点只查一次，不凭感觉估。
-
实测粒度=写作粒度：时刻表每段里程/耗时须有对应独立实测条目；仅有整体实测值时只允许整段书写，中途点位只标"约第X小时到，估算"，不得把整体值拆成多段充当实测值。

### 5. 排固定锚点

- 长线自驾先把主干道施工/封闭/绕行通告当第一锚点核（官方通告优先于攻略转述，封闭段直接改写走法与聚簇），再核航班/火车班次、预约场次与放票提前天数、闭馆与停检时刻、日出日落、潮汐、光线时段。
- 锚点从官方渠道核实、核口径先核发布日期（旧年份页面换新源），写进对应日程行；查不到确切口径的标"待核实"。

### 6. 排每日主线

- **骨架容量核对（排主线之前做）**：必去层 + 签名外延层逐项列出实测所需天数/小时，与总天数容量核对；总量 > 容量时 **先输出"
  骨架冲突清单"**（各段实测代价 + 置换方案），结合景区重要性与代表性、时间预算进行取舍。
- 密度两头看—— **太赶**（赶不上锚点、游览时间低于该点实际所需、用餐排不上、缓冲为负）就放宽、拆天、砍点； **太空**
  （半天只有可选项或占位项、纯赶路无内容）就从备选池换入，或把后面某天的重项前移匀衡——总天数是诉求定死的，"压缩天数"不可用。
- 可压缩日：排程中标记含二刷/可砍项/低价值项的日子为可压缩日，作为总天数锁死时换入签名外延/推荐层点的置换来源；无此类日子时，才判为不可换入。
- 加减天数：总天数锁死时若加签名外延/推荐层点，按可压缩日优先给出总天数不变的置换方案。

- 相邻两天一天塞满、一天半空即失衡，优先重排全局而不是各打补丁。
- 排程时即执行第 9 节终检闸门（不留白、时间轴相接、用餐节奏），不要排完再回头补。
- 长线自驾逐日看：加油/充电间距 vs 续航、无信号段（提醒下离线地图）、夜路能避则避，避不开就给关门条件（"X
  点前未过某地则改住某镇"）——赶日落/末段入园的日子按天黑时刻倒排全天。
- 高海拔线路首日留适应余量、给降海拔备选。
- 首尾日按落地/起飞时刻实事求是：落地晚就轻排市区，不硬塞远线；尾日留还车弹性，给可选项不给空白。
- 硬日≠合格日：单日纯驾≥8h、或纯驾+游览≥12h
  时，必须执行放宽/拆天/砍点之一并重排该日，不得以"硬日"标注+关门条件替代重排；确因必去点冲突无法避免的，须把该必去点的实测代价（额外里程/耗时）写入取舍说明。
- 硬日触发重排时，砍点顺序：备选层→推荐层→签名外延层→必去层；砍推荐层前先试调住宿/顺序/走廊；砍时在取舍说明写实测代价和换入条件。

### 7. 选住宿区域

动线终点兼次日出发点，油站/餐饮/海拔作筛选条件；能连住就连住（少搬行李、留二刷空间）。每晚给地点+为什么+价位档。

### 8. 生成预算与预订清单

按输出第 3 节做，预订项按紧迫度排序。

### 9. 风险校验与自检（终检闸门）

- 方向：不复核「顺时针/逆时针」这个词，改核判据句。按节点序列取两组对弧，弧段走向组合必须与所标方向自洽：南弧向西＋北弧向东＝顺时针；南弧向东＋北弧向西＝逆时针。组合矛盾、或只写了术语没写判据句 → 不合格。复核行不得复述上游结论（含子 Agent 的自我声明），必须给出本层独立判据。（有坐标与计算工具时，加算有向面积作第二判据：负=顺时针、正=逆时针。）
- 风险：逐项过天气/封路/季节性封闭/闭馆日/满员/限行/高原，每个关键依赖（住宿/交通/门票）至少一个备选。
- 一致性核对：
    - 每日时间分段加总 = 当日总量
    - 交通里程分段加总 = 当日总量；凡标"估算拆分"的段，加总不得超出其来源整体实测值
    - 同一数值全文同源
    - 到访日与闭馆日对得上
    - 关键事实（封闭段、停检时刻）与账本一致
    - 总览方向与节点序列按地图转向一致；不一致时改方向，不迁就标签。
- 硬日门槛（安全硬规则，无豁免）：逐日算纯驾时长，≥8h 即触发重排检查；确认无法重排的，核对取舍说明是否列出对应必去点的实测代价。
- 时间轴连续性：按时刻逐行相接（上行结束=下行开始），未分配时间缝 >10min 判不合格，须并入相邻行或重排该日；≤10min 的接缝余量并入相邻行并显式标注。倒排日重点查正排段与倒排段的接缝。
- 接驳行核对：逐日检查住宿↔景区/停车场↔观景台之间，凡跨坐标即有行；无实测值的先补测，不得用相邻行的时间缝默许通过。
- 留白与注水：逐日核对用餐、休整、入住放行李等支撑行为时长是否明显超出常规；超出且无理由即为注水，须重排该日（推迟出发、压缩或换入内容）。按第 4 节显式定义的缓冲不算留白。
- 相邻休整+用餐：视为同一段合并计时，合计 >45min 须压缩、合并或推迟出发；确需长餐（如地方特色正餐）写明理由。
- 用餐节奏：①相邻两顿正餐间隔 ≥3h，且中间至少夹 1 项非用餐实质安排，不满足须写明理由（如早午餐、航班日）；②晚餐不早于 18:00 与当日日落前 1h 中的较晚者，早于此须写明理由，作息明显偏晚的目的地（如新疆）可按当地习惯调整并注明；③14:00 后迟午餐时，晚餐 ≥ 午餐结束后 3h。
- 必去层逐项点名：已排入，或进取舍说明带代价——不无声缺失。
- **签名外延点名闸门**：凡标记为签名外延的点/走廊，终答前逐项确认——①已在每日时刻表；或②取舍说明中附结构化置换方案（砍项、换入代价、换入后全天时长、是否硬日，四项齐备）。两者皆无 → 不合格，回炉重排；仅有"+X km/+X 天"数字的取舍说明判不合格。
- 推荐层逐项点名：必须出现在每日时刻表、取舍说明、避雷之一；取舍说明含净增数据；顺路安全点须在对应路段备注"安全区短停"或"不经过原因"；因总天数锁死被砍时，取舍说明须含总天数不变的置换方案（可压缩日+砍哪些项+代价），否则不合格。
- 时刻表格式闸门：按输出第 2 节逐行核对——时间为区间、一行一动作、长驾日休整单列成行（见第 4 节）、用餐标注性质；交通行的安排须同时具备起点和终点，里程·耗时须同时具备里程与耗时，不可遗漏或编造。
- **领域数据对账闸门**：终答前核对行程中的地点、路线、锚点、约束、风险和支撑动作时长预算是否已按
  `travel-fact.schema.json` 入账；`itinerary.schema.json` 产物与 Markdown 时刻表的日期、事件顺序、
  交通方式和时长必须一致。发现支撑动作低于其入账预算、缺少前置条件或时间轴被挤压时，重排行程或补足依据，
  不得只改 Markdown 数字。
- **现实动作预算闸门**：逐个核对 meal / lodging / fueling / ticketing / preparation / rest 等事件。
  每个有现实操作成本的事件应声明或可追溯到 `duration_budget`；`event.duration` 低于所选 context 的
  `normal` 时，必须满足 `compressed/minimum` 的全部前置条件。否则选择其一修复：延长动作、改变执行 context、
  提前完成前置准备、更早出发、更换住宿/餐厅、削减景点或重排当天。不得通过改名或拆行规避预算。
- **交通方式一票否决闸门**：逐行复核取车后到还车前的跨节点交通行。用户要求自驾时，
  出现停车后换乘国内航班/火车/长途客车、租车闲置形成飞地，均判不合格；披露成本或提供备选不能使该主方案合格。
- 多版本终检：逐版本执行本节自检后，再按「多版本规划纪律」核验版本契约、路线结构假设、版本专属检索、
  硬性版本分离指标和标签互换测试。六项结构指标（主干节点重合率、住宿城市序列差异、远端走廊取舍、
  单日驾驶结构、景点覆盖数量、看图可感知差异）必须逐项给出数值或明确 PASS/FAIL，并有行程/账本证据；
  另必须给出「交通方式一致性」PASS/FAIL 与逐日交通行证据，该项为版本分离的前置一票否决指标；
  缺项、只有结论无证据、或未达版本契约设定时打回重排。重排后仍不可分离时，核验「横向对比」是否披露约束冲突和用户待取舍选项。
- 自检发现问题改行程本身，允许局部重排。

## 输出

单版本输出下方 1–6 项，最后输出「来源」。多版本任务只额外增加一个「横向对比」章节，放在所有版本之前；每个版本仍完整输出 1–6 项，全文最后输出「来源」。除「横向对比」外，多版本任务不得新增任何其他章节；共用事实、默认假设或父级核对结果只写入受影响版本对应章节，不得另设汇总章节。

章节标题必须使用本节列出的名称原样，不得附加括号、口径说明或补充说明。

1. **一页总览**：节点序列（便于粘进地图 App 串路线）、方向（判据句式：「南弧向西＋北弧向东 → 顺时针」；不得只写术语。术语与判据不一致时以判据为准）、所选路线结构类型与主要替代结构、交通方式与线路范围一致性结论、总里程与天数、逐日纯驾结构、节奏档位、预算区间、最佳出行窗口、默认假设清单（可改项）。

2. **每日时刻表**：
    - 时间/安排/交通方式/里程·耗时/费用/备注，一行一个时段；跨节点交通行必须与用户指定方式一致；
    - 预约、闭馆、日落等锚点写进对应行；
    - 加油与服务区休整排进时刻表行（标注服务区/城镇名或"以导航实时为准"），当日可砍项随行带出；
    - 住宿一行（地点 + 为什么 + 价位档）。
    - **时间列统一成区间**（如 12:00-13:00 落地取车），事件行也给结束时刻，别留半开区间。
    - **时刻表每行不得耦合两类动作。**
    - **用餐行须标注性质**：正餐 / 小吃·下午茶（非正餐）/ 夜市小吃（非正餐）；同一日正餐不超过 2 顿。
    - **用餐行不得作为时段填充物**：某时段无真实内容可填时，宁可延长前项或推迟出发，不得用"晚餐"拉长时间。

3. **预算与预订清单**：
    - 预算分类目给区间（大交通/当地交通/住宿/门票/餐饮/机动金），总预算与人均，超预算给降级替代；
    - 预订按紧迫度排序，逐项给渠道、放票/提前天数、退改规则、当前可约状态。

4. **风险与备选**：天气/封路/高原/闭馆/满员的 Plan B；每个关键依赖（住宿/交通/门票）至少一个备选。

5. **取舍说明**：仅在存在未排入的必去、签名外延、推荐点或已拒绝路线结构时输出；未排入项附实测换入代价，签名外延须用第 9 节四要素置换方案；被拒路线结构须给出结构差异、预估里程/驾驶结构与拒绝理由。

6. **调整入口**：告诉用户改哪里最有效（换方向、换档位、加减天数、换必去点——换方向动全局动线，其余只动受影响的天）。

7. **来源**：集中列出正文引用的事实来源；正文不放链接。

多版本的「横向对比」必须逐版本对照版本契约，呈现主目标、保护约束、实际取舍、用户可感知差异、适配场景和约束冲突，
并在该章节内加入「版本分离核验」表/段落（不得另设顶层章节），逐项列出：主干节点重合率（含共同主干与独有节点/路段）、住宿城市序列差异、
远端走廊取舍、单日驾驶结构、景点覆盖数量、看图可感知差异、交通方式一致性。所有断言须来自最终行程与事实账本，
不得按版本名或子Agent自述凭印象概括。

**文风**：可执行优先——短句、数据带单位（km/h/¥/m）、少形容词；正文不放链接，来源集中列文末；图片可选、克制。

**边界**：不代订、不代付；价格与政策以官方和现场为准。
